# Development Guide

## Prerequisites

- Node.js (LTS)
- npm

## Setup

```bash
npm install
npm run dev          # starts Next.js dev server at http://localhost:3000
```

The SQLite database file (`dev.db`) is created automatically on first run. It lives at `prisma/dev.db` (gitignored).

## NPM Scripts

| Script | What it does |
|---|---|
| `npm run dev` | Start Next.js dev server (hot reload) |
| `npm run build` | Production build |
| `npm run start` | Start production server |
| `npm run lint` | Run ESLint |
| `npm run db:seed` | Seed sample data using `jiti prisma/seed.ts` |
| `npm run db:reset` | Drop and recreate the database (`prisma migrate reset --force`) |
| `npm run db:studio` | Open Prisma Studio GUI at `http://localhost:5555` |

## Database

### Running migrations

```bash
npx prisma migrate dev --name <migration-name>
```

This updates `prisma/migrations/` and regenerates `src/generated/prisma/`.

### After changing `schema.prisma`

Always run `prisma migrate dev` — do **not** just regenerate the client. The migrations folder tracks schema history.

### Seeding

Two ways:
1. **Via API (recommended):** `POST /api/seed` — click "Reset & Load Sample Data" in the Settings tab, or `curl -X POST http://localhost:3000/api/seed`
2. **Via CLI (workaround):** `npm run db:seed` — uses `jiti` to execute `prisma/seed.ts` directly

The CLI path exists but can have ESM resolution issues. The API route is the reliable path.

### Database location

- Default: `prisma/dev.db` (relative to project root)
- Override with `DATABASE_URL` env var: `DATABASE_URL=file:./custom.db npm run dev`

## Environment Variables

| Variable | Default | Description |
|---|---|---|
| `DATABASE_URL` | `file:./prisma/dev.db` | SQLite file path |

No `.env` file is required for local development — defaults work out of the box.

## Prisma Quirks (v7)

### Driver adapter is required
Prisma 7 does not support SQLite without an adapter. The `PrismaBetterSqlite3` adapter must be instantiated and passed to `PrismaClient`. See `src/lib/db.ts`.

### Generated client location
Output is `src/generated/prisma/` (configured in `schema.prisma`). This is ESM-only. Import from:
```ts
import { PrismaClient } from "@/generated/prisma/client";
```

Do **not** import from `@prisma/client` directly — the generated output is the client.

### Singleton pattern
`src/lib/db.ts` uses the `globalThis` singleton pattern to prevent multiple client instances during Next.js hot reload in development.

### `prisma.config.ts`
Generated by Prisma CLI. Reads `DATABASE_URL` from env. The `datasource.url` here is only used by CLI commands (`migrate`, `studio`), not by the running app — the app gets the URL from `src/lib/db.ts`.

## Adding a New Feature

Follow the modular pattern — don't couple new features to existing task logic:

1. **Add Prisma model** in `schema.prisma`, run `npx prisma migrate dev --name <name>`
2. **Add API routes** in a new `src/app/api/<feature>/` folder
3. **Add components** in `src/components/`
4. **Add TypeScript types** in `src/types/index.ts`
5. Wire up in `page.tsx` only what's needed for the tab/view

## Known Issues & Gotchas

- **No drag-and-drop reorder** — `position` is append-only right now
- **No optimistic UI** — every mutation re-fetches all boards; may feel slow with large datasets
- **`tags` is a JSON string** — always parse/stringify it, never push to it directly
- **Next.js 16 breaking changes** — route handler params are a `Promise` (`await params`); do not use old synchronous pattern
- **Tailwind v4** — uses PostCSS plugin (`@tailwindcss/postcss`), not the old `tailwind.config.js` setup
